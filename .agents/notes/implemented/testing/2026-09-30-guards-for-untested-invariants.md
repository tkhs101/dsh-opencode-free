# Agent Note: 补齐变异验证暴露的六个测试缺口

Status: implemented

## Problem

第一轮审计的第二遍用**变异测试**（删掉一行生产代码，看有没有测试变红）审了测试体系本身，找出六个"删了没人拦"的缺口：

- `gateInflight` 单飞、`runSingle` 单飞、`writeCacheAtomic` 的 rename、`readProbes` 的字段校验——四个删掉都 88/88 全绿。
- `PROBE_MAX_TOKENS` 的覆盖参数与 `usage` 透传没有任何断言，而它们的唯一消费者 `probe-ab.mjs` 正是"1024 而非 16"那个决定的证据来源。
- `probeProgress` 的实时测试把每模型的轮次内快照收进 `seen` 之后**从未断言**——这条唯一以"实时跟踪"为职责的测试，在最需要的位置放弃了。

## Decision

逐条补测试，并对每条做**变异验证**——用删掉被守护的那行代码证明它会红。

其中两条在写的过程中暴露了更深的问题：

- `readLastRound` 的 `total` 校验：`{ total: 0 }` 这个用例删掉 total 校验后仍然全绿，因为 `done` 校验把它拦了。补 `{ total: 0, done: 1 }`——在其它维度都合规，只有 total 校验能拒——才真正锁住。**一个看起来覆盖了某个分支的用例，可能根本没覆盖它。**
- `probeProgress` 的快照拷贝断言：我第一版的 `unmount()` 顺手清了 harness 的定时器表，于是"轮询链是否停止"的测试无论 cleanup 有没有都绿。清掉之后，删掉 `results: { ...probeRun.results }` 的拷贝才会让它变红。

## Alternatives considered

- **只加计数断言**（"删掉守卫应该变红"），不写具体行为断言。论据是快。否决：计数变红只能说明"有东西被测到"，不能说明测的是**正确的东西**——上面那条 `total` 的例子正是计数够用而语义没测到的形态。
- **把 `probeProgress` 的实时性交给端到端测试**。否决：那是渲染层的事，而这里的性质是"轮次在改的同时 `probeProgress()` 给出的是快照"，只能在数据层断言。

## Consequences

- **收益**：六个缺口全部有守卫，每条都经变异确认会红。`catalog.test.mjs` 从 88 增至 99 条。
- **代价与已知上限**：变异验证本身是手工的（逐条手工替换），没有自动化。将来若再有大改动，值得把它做成脚本——但那时需要的不是工具，而是"哪些不变量值得被守护"的判断，那一份在 `docs/adr/` 与本目录。
- `a torn write is never observable` 里原本有一条"写入进行中目标名不存在"的断言被**删除**：小载荷在读之前就写完了，那是一条竞态断言，偶尔能看到临时文件、更多时候看不到——看起来有覆盖，实则没有。改成确定性断言：孤立的临时文件必须被读成"无缓存"，绝不读成前缀。
