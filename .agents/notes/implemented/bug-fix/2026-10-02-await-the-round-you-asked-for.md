# Agent Note: 卡片得知道自己在等哪一轮，通道得在它被画出来时就生效

Status: implemented

## Problem

上游第二次审阅确认了上一轮五条全部修好，又提出两条。两条都不是新功能，各是一处「结论公布得比它所描述的事实晚一步」。

**闸门慢时 UI 在新轮开始前就收尾。** 后端 `runProbeRound` 先 `await refreshGate()` 才发布 `probeRun = {running:true}`，而闸门只是一次廉价 GET。轮询间隔 800ms，于是慢一点的后端会让卡片先读到**上一轮**的报告——它看起来是「已完成」。手动点击那条路径其实已有防护：`probe()` 显式识别「POST 已确认这一轮存在，但首读可能还是上一轮」并保持轮询。漏的是第二次 tick：轮询链把同一个 reading 交给 `adopt()`，那里把 `awaiting` 消费掉并 `stopPolling()`。按钮回来了，面板定格，而真正开始的那一轮再也没人看。

**成功模型在通道生效前就被显示。** 上一轮我把 `applyMeasuredChannel()` 放在整轮结束后。但每模型的结果是**逐个**画上去的：面板已经显示某个模型成功时，它仍在走探测刚排除的那条通道。轮是串行的，剩下每个慢模型各占满 15 秒超时——这个不一致窗口可以很长。这条是我上一轮改动的直接后果。

## Decision

- **用轮次戳区分「我等的那一轮结束了」和「这是上一轮」。** 每一轮都有 `startedAt`。点击时把当时屏幕上的那一轮的 `startedAt` 存进 `pollRef.current.saw`；`adopt()` 与 `probe()` 的首读分支都用同一处判断：finished 且戳仍等于 `saw`，就是还没轮到我们，继续等。等待有 30 秒上限，后端真的没起轮时不会永远轮询。没有轮次 id 就不需要改缓存格式。
- **等的时候不重画。** `startPolling(null)` 而非 `startPolling(reading)`——否则会顶着忙碌的按钮把上一轮的报告画出来，正是这个分支要避免的困惑。点击时已经清空进度区了，真正的 reading 到达时会重新画。
- **逐模型施加测得的通道。** `applyMeasuredChannel()` 从轮末移进循环里 `outcome.kind === "ok"` 之后。缓存仍然整轮只写一次——半个轮次不能被读回成完整的结论集。

## Alternatives considered

- **后端提前发布 `running:true`（pending）**——被上游提过，也确实更小。但会出现一个 `total` 尚未知的「启动中」，且若后端最终没能起轮，前端仍需超时兜底；等于把同一个竞态换个地方再补一次。戳方案不动后端。
- **给轮次加 id**——最精确，但要多改缓存格式、读回守卫和全部相关测试，为一个已有戳可用的问题不值得。已写入戳来自 `deps.now()`，理论上同一毫秒可能撞，但一轮至少隔着一次闸门 GET，且 30 秒上限是兜底。
- **`awaiting` 一直为真直到看见 `running:true`**——否决：卡在两者之间的快轮次（闸门已缓存）会被按上一轮处理，把按钮按住 30 秒。戳比较没有这个漏洞。

## Consequences

- 点击后到新轮出现之间，面板保持清空且按钮忙碌——这是准确的：确实还没有本轮的任何结果。
- `pollRef` 多两个字段（`last` 与 `saw`），都在 ref 上，不闭包渲染态。
- 通道改动早至每模型之后，因此「已显示成功」与「已按测得通道路由」不再有窗口差。
- 两条各有守护测，都做过变异验证：改回去对应测试即失败（#1 失败在按钮被提前释放，#2 失败在中途路由断言）。
