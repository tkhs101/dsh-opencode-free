📝 总体评估

📋 总体评估

项目概况：dsh-opencode-free 是一个发布到 npm 的 DeepSeek Harness 插件（MIT），TypeScript 源码在 src/，构建产物 lib/ 由 tsc 生成且已被 .gitignore 排除（已用 git check-ignore 与 git ls-files lib 核实）。运行时依赖为零，4 个 peer 依赖全部由宿主提供，devDeps 只有 3 个。核心机制：以 models.dev 的 api.json 作为「哪些模型免费」的事实源，以 GET /zen/v1/models 作为可用性闸门，再由一次顺序探测轮次给出「是否已下架」的终局判决。它有两个不常见的性质：一是刻意冒充 OpenCode CLI 的身份以通过上游的匿名免费层准入（这一点在 CONTEXT.md、docs/reverse-engineering.md、README 里都被主动、诚实地记录下来，连术语都区分了「仿冒」与「bypass」）；二是它把「无法判定」与「判定为否」严格区分——整个项目的注释密度与 ADR 制度都围绕这一条不变量建立。

项目地图：运行时只有两个入口。宿主侧 apply()（src/index.ts:336）构建一个 Catalog（src/catalog.ts:774，目录的唯一所有者）、一个 zenProvider()（src/zen-provider.ts:1701，传输与身份的唯一所有者），向 ctx.llm 注册 PiAiAdapter，并注册三条同源 HTTP 路由。浏览器侧 src/client.js 是手写的 ModuleLoader bundle，渲染插件详情页的「模型显示」卡片，只读宿主目录、写回 hiddenModels。持久化只有一个文件：$DSH_HOME/dsh-opencode-free/catalog.json，存放 models.dev 的 models 字典、探测判决与上一轮报告。出网目的地恰好两个：models.dev 与 opencode.ai/zen/v1。测试 146 个；其中 compatibility.test.mjs 的 26 个并非 hermetic——它不设 DSH_HOME，会读写开发者真实的 ~/.dsh/dsh-opencode-free/catalog.json 并真实访问 models.dev（见 #40）。

主要风险：四条高危。前两条是实证确认的逻辑缺陷：其一，全局 fetch 守卫 patchGlobalFetchForZen 的外层 catch 会接住内层已重新抛出的网络错误并再发一次请求，而重发用的是未改写的 init，实测一次用户调用变成两次上游请求、第二次 Authorization 为 null——网络抖动因此被伪装成「匿名层被拒」的 403，本项目着力建设的整套故障诊断机制在这一行被抵消。其二，目录发生全量重新下载时 lastRound 报告被静默删除，而仓库里那条宣称守护该不变量的测试只驱动了 304 分支，把两个分支都当成了已覆盖——这是一枚真实的假绿。第三条，README 与 AGENTS.md 推荐的安装校验命令 dsh --profile web --dump-config 在 DSH 实现中零脱敏（已在宿主源码中核实），会把用户按 README 写进 cordis.patch.yml 的 Zen key 原样打到 stdout，而 AGENTS.md 自己在第 10 行写着「Never print API keys」。第四条，README 与 AGENTS.md 都让用户安装 @0.3.1，而 npm registry 实测 latest 仍是 0.2.1，0.3.0 与 0.3.1 从未发布——新用户的安装第一步就会失败。

亮点：这不是一个「看起来还行」的项目。证据密度、失败模式的自我归因、以及对「上游会漂」这一事实的承认都很少见：PROBE_MAX_TOKENS = 1024 旁边挂着一次真实 A/B 的完整数据与推翻过程；refreshGate 的 DISJOINT 护栏来自「空列表检查不够用」的正确直觉；探测判决要求扫完全部通道才允许写 dead，直接堵住了「路由判断错了就永久删掉一个能用的模型」这一曾经真实发生过的 bug，而 .scratch/model-probe/issues/01-*.md 把教训（用会覆盖的单变量去记录可能发生多次调用的路径，读到的必然是最后一次）完整留档。我实测验证了闸门的四条分支：真实下线会收窄，而空数组、裸字符串、外来租户三种畸形回答全部被正确忽略。安全侧的凭据不落盘、缓存只存 models 字典、同源栅栏、cache-control: no-store 都做对了。146 个测试连续两次运行零失败、命名即不变量；但 26 个并非离线，会写真实用户缓存并访问真实网络（#40）。

第二轮（变异测试）追加的发现：用「删掉这行代码，看测试会不会红」的方法对测试体系本身做了一遍审计，追加 12 个发现、5 个高危。最重要的一条修正了我在第一轮的错误结论：我曾写「146 个用例全部离线」——这是错的。compatibility.test.mjs 导入构建产物并在顶层调用 apply()，却从不设 DSH_HOME，于是它把开发者真实的 ~/.dsh/dsh-opencode-free/catalog.json 当沙箱读写，并真的访问 models.dev（实测缓存里带着真实 etag W/"58e29fa…"）。本机那份 80KB、含 33 条探针判决的缓存，正是在我执行 pnpm run check 时被覆盖的——这是该缺陷的现场演示。第二条更要命：那条断言「重验证不会抹掉报告」的测试根本没有发生重验证——它不传 ttlMs（默认 24 小时），却只把时钟推进 6 小时 1 分，因此 stale() 恒为 false、ensureFresh() 一次请求都不发；变异测试显示删掉被守护的修复后 88 个用例仍然全绿。其余三条高危是两个单飞守卫零覆盖（删除后 88/88 全绿）与 writeCacheAtomic 的原子性零覆盖（测试名里有 "atomically"，但把临时文件 + rename 整个删掉也没人拦）。

优先修复：第一梯队是 #1、#2、#3、#4 与 #40——全部是十几行以内的局部修复，收益分别是：新用户能装上、key 不外泄、故障诊断可用、状态诚实、测试不再破坏开发机。其中 #40 是本次审计唯一一条「先修它、否则你连测都不可信」的发现：在它修好之前，任何依赖 pnpm test 的验证结论都建立在一个会污染真实状态的沙箱之上。第二梯队是发布纪律：M5（未发布变更挂在已发布版本号上）、M6（Node 24+ 从未进 CI）、M7（action 未按 SHA 固定）、M20（无发版闸门）。第三梯队是结构性：身份头七件套的四处重复、三处可选 peer 依赖与无条件 import 的矛盾、客户端轮询链在卸载后不停（M3）。可访问性的两项（M18、M19）是纯 CSS 改动，半天可以全部达标。

总评：B（6.6）。工程判断力与自我批评密度明显高于同类项目均值，没有发现严重级问题；扣分集中在四个会真实伤到用户的高危项——其中两个是代码缺陷，两个是发布/文档缺陷，且都属于「照着 README 走一遍就会撞上」的类型。当前状态下不宜按 README 所写的方式公开发布 0.3.x；修完四条高危后，这个项目的工程质量足以排到 A 档。
